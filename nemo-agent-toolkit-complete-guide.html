01 Overview & Identity

NAT does not replace your agent framework — it wraps and supercharges it. The core insight: every agent, tool, and workflow is a composable function, defined in YAML and discoverable across the whole ecosystem.

04 Configuration (YAML)

One declarative file describes the whole application. Each block is a map of instance-names → objects, and a _type discriminator selects the implementation.

# every block keyed by your chosen name; _type picks the implementation
general:
  telemetry:
    tracing: { phoenix: { _type: phoenix } }      # observability
llms:
  main: { _type: nim, model_name: meta/llama-3.3-70b-instruct, temperature: 0.0 }
embedders:
  emb:  { _type: nim, model_name: nvidia/nv-embedqa-e5-v5 }
retrievers:
  vs:   { _type: milvus_retriever, uri: http://localhost:19530, embedding_model: emb }
memory:
  saas_memory: { _type: redis_memory, host: localhost, embedder: emb }
functions:
  search: { _type: nat_retriever, retriever: vs, topic: docs }
workflow:               # the top-level agent IS a function
  _type: react_agent
  llm_name: main
  tool_names: [search]
eval: { ... }            # datasets + evaluators (see §12)

🧬 Config inheritance

Top-level base: key names a parent config; deep-merge override. Supports chained inheritance and circular/missing-base detection.

🔧 --override

--override llms.main.temperature 0.7 — dotted path uses the instance key, value is type-coerced. Repeatable.

🔑 Interpolation

${VAR}, ${VAR:-default} only (no bare $VAR). file://path.txt loads file content into a string field.

📄 .env + validate

CLI auto-loads .env (exported vars win). nat validate --config_file F checks a config before running.

10 Human-in-the-Loop

Any function can pause to ask a human, via Context.get().user_interaction_manager.prompt_user_input(...). No global "enable HITL" flag — you wire an approval tool and reference it.

Prompt types: text · binary_choice · radio · checkbox · dropdown · notification · oauth_consent. nat serve supports all; nat run supports text only.
# inside a @register_function tool
from nat.builder.context import Context
from nat.data_models.interactive import HumanPromptText
resp = await Context.get().user_interaction_manager.prompt_user_input(
    HumanPromptText(text="Approve? (yes/no)", required=True, timeout=60))
ok = "yes" in resp.content.text.lower()

Sizing calculator (nat sizing calc): runs your workflow at several concurrency levels, fits a least-squares line on p95 latency, and estimates GPU count for target users/runtime. Slope >1 ⇒ worse-than-linear scaling.

13 Self-Improvement

Three escalating levers — all driven by the same eval metrics.

The optimizer searches optimizable_params+search_space on functions/LLMs and keeps the Pareto front of your eval_metrics.
llms:
  main:
    _type: nim
    optimizable_params: [temperature, model_name]
    search_space: { temperature: { values: [0.0, 0.3, 0.6] } }
optimizer:
  eval_metrics:
    accuracy: { evaluator_name: accuracy, direction: maximize }
    token_efficiency: { evaluator_name: token_efficiency, direction: minimize }
  numeric: { enabled: true, n_trials: 24 }
  prompt:  { enabled: true, ga_generations: 3, ga_population_size: 3 }

18 Watch It Live: opt into telemetry & visualize every run

Observability is opt-in and code-free: add an exporter under general.telemetry.tracing, point it at a viewer, and every LLM call, tool call, latency and token count streams into a UI as the agent runs. Multiple exporters can run at once; under the hood it's OpenTelemetry/OTLP (Weave uses the W&B SDK).

One run, fanned out to any number of viewers. Each shows the same span tree with per-step latency and token counts.

⚡ Fastest path — local Phoenix in 3 steps

# 1 · install the exporter
pip install "nvidia-nat[phoenix]"

# 2 · launch a local Phoenix viewer (UI at http://localhost:6006)
docker run -it --rm -p 6006:6006 -p 4317:4317 arizephoenix/phoenix:latest

# 3 · add this block to your config, then `nat run` / `nat serve` as usual
general:
  telemetry:
    tracing:
      phoenix:
        _type: phoenix
        endpoint: http://localhost:6006/v1/traces
        project: my-agent
🔭

Open http://localhost:6006, pick your project, and watch traces appear in real time as you run the agent. Each trace is a span waterfall — the LLM and tool calls with their latency, token counts, inputs/outputs, and the exact call tree. This is how you find where time and tokens actually go.

19 Zero → Production: the full journey

The toolkit's features make sense as stages of one journey. Here's the path from a blank folder to a hardened, observable, self-improving production agent — with the command and the "done when" for each stage. (The text-to-SQL example in this repo walks the same path end to end.)

Each stage adds one capability and has a concrete exit criterion. You don't skip ahead — you can't improve what you can't measure, and you don't ship what you haven't observed.
StageWhat you doCommand / config added✅ Done when
0 · Prototype Write the agent in your framework (e.g. LangGraph). Scaffold a package. Minimal config: one llm + a workflow. nat workflow create my_agent
nat run --config_file config.yml --input "…"		 It returns an answer to a hardcoded question.

2 · Observe 👁️ Add a tracing exporter (Phoenix is easiest) and watch every LLM call, tool call, latency and token count live as it runs. (See §18.) tracing: { phoenix: { _type: phoenix } } + launch Phoenix You can see where time and tokens go, step by step.
3 · Measure 📊 Build an eval dataset; add an evaluator that scores what matters (e.g. a custom execution-accuracy evaluator for SQL). Get a baseline of accuracy + latency + token cost. nat eval --config_file eval.yml --reps 3 You have a quantified baseline you can beat.
4 · Improve 📈 Apply high-value techniques, then let the optimizer search the space (Pareto of accuracy↑ / tokens↓ / latency↓). Optionally fine-tune a smaller model. nat optimize --config_file optimizer.yml
(then nat finetune …)		 Measurably better than the Stage-3 baseline, at acceptable cost.

🧭

The one rule: never skip a stage. You can't improve (4) what you can't measure (3), and you can't measure what you can't observe (2). Most agents that "work in a demo but fail in production" jumped from Stage 1 to Stage 6.

🧪

Worked example: the text-to-SQL agent in this repo (nemo-sql-agent/) walks Stages 0–4 literally — a LangGraph agent → @register_function → LangSmith tracing → a custom sql_execution_accuracy evaluator → nat optimize over the proven technique switches. Its docs/GUIDE.md is the evidence base for which improvements to make in Stage 4.

20 Live Data & Anomaly Detection

⚠️

Architectural truth first: NAT is request/response — no native stream engine, no scheduler/cron, no always-on listener (the front_ends/cron/ dir is an empty stub). "Live data" means either you push events to the API, or the agent pulls via tools. NVIDIA's own alert_triage_agent proves it: its "live" mode is a custom external Flask server that calls the workflow per alert.

The proven pattern (from alert_triage_agent): a cheap deterministic gate + detector turns a stream of events into a few candidate alerts; the agent investigates only those, then a categorizer labels and prioritizes them for a human. The LLM is spent only on what survived the filters.

Gate + detector are deterministic and always-on; the LLM agent only sees what they flag. This is the alert_triage_agent shape — and the repo's runnable nemo-sql-agent/anomaly/ demo.
